# State Model

## Authoritative root

The future engine likely requires a versioned `WorldState` containing:

1. Simulation metadata.
2. Time.
3. Random state.
4. Countries.
5. Institutions.
6. Leaders and factions.
7. Regions and territory.
8. Population.
9. Economy and markets.
10. Infrastructure networks.
11. Military organizations.
12. Platforms and formations.
13. Inventories.
14. Technology and doctrine.
15. Diplomatic relationships.
16. Plans and operations.
17. Intelligence sources and observations.
18. Faction belief stores.
19. Event queue.
20. Historical and scenario metadata.

## Stable identity

Every persistent object needs:

1. Stable identifier.
2. Type.
3. Version.
4. Creation event.
5. Current status.
6. Owning or responsible actor where applicable.
7. Spatial representation where applicable.
8. Lifecycle.

Names and labels may change. Stable identity must not.

## Core object categories

### Entity

A persistent object with identity, such as a country, formation, platform, city,
base, satellite, institution, or leader.

### Aggregate

A summarized quantity or collection that can be conserved and, where supported,
expanded into subordinate objects.

### Network

Nodes and edges representing transport, energy, communications, trade,
logistics, command, or alliance connectivity.

### Flow

A quantity moving through a network over time.

### Stock

A quantity held by an entity or location.

### Plan

A structured intended sequence with objectives, assumptions, phases, capacity,
review, and abort conditions.

### Operation

An executing plan consuming assets, resources, authority, and time.

### Observation

Raw or processed evidence generated by a source.

### Claim

An analytic assertion with confidence, provenance, time, and alternatives.

### Track

A maintained belief about an entity, formation, event, or pattern.

### Command

A request by a player, AI, institution, or system.

### Event

An authoritative state transition.

## Component versus object model

A future design study should compare:

1. Entity component systems.
2. Relational state.
3. Typed object graphs.
4. Hybrid approaches.

The decision should optimize:

1. Determinism.
2. Serialization.
3. Queryability.
4. Agent comprehension.
5. Testability.
6. Performance.
7. Schema evolution.

## Derived state

Derived values should be recomputable from authoritative state whenever
practical.

Examples:

1. Available mission range.
2. Regional energy sufficiency.
3. Formation combat power.
4. Alliance access.
5. Publicly displayed confidence summaries.

Cached derived state requires invalidation rules.

## State ownership

Every authoritative field must have one owning system. Several systems may read
it, but only the owner emits events that change it.

## Invalid state

The engine should reject or detect:

1. Duplicate identity.
2. Missing owner.
3. Negative conserved stocks.
4. Platform in two incompatible places.
5. Conflicting exclusive operations.
6. Event referencing a nonexistent object.
7. Belief incorrectly stored as truth.
8. Truth directly exposed to an unauthorized faction.
