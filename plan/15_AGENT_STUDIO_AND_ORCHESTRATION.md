# Agent Studio and Orchestration

## Core principle

Use a coordinated studio, not a flat swarm.

Ten agents may be active, but only two or three should write unrelated production
code simultaneously during a future development stage.

## Persistent roles

The canonical ten roles are defined under `Agents/`.

## Why unrestricted swarms fail

They tend to create:

1. Duplicate state models.
2. Conflicting terminology.
3. Several event systems.
4. Features that work alone but not together.
5. Unmergeable branches.
6. Hidden rule logic in interface code.
7. Weak tests.
8. Large volumes of superficially complete work.

## Canonical coordination artifacts

1. Game constitution.
2. Domain model.
3. Simulation invariants.
4. Command and event contracts.
5. Abstraction ledger.
6. Decision log.
7. Source registry.
8. Agent charters.
9. Ownership map.
10. Structured task queue.
11. Regression scenario library.
12. Performance budgets.

## Future task packet

Every agent assignment should contain:

1. Objective.
2. Player decision.
3. Relevant game rule.
4. Allowed files.
5. Forbidden files.
6. Existing interfaces.
7. Required invariants.
8. Acceptance tests.
9. Performance limit.
10. Expected deliverables.
11. Assigned reviewer.
12. Integration owner.

## Future workflow

1. Game Director selects one bounded objective.
2. Core Gameplay Designer defines the player experience.
3. Simulation Architect approves state contracts.
4. QA Lead defines failure cases.
5. Implementation agents work in isolated Git worktrees.
6. Specialist reviewers inspect the behavior and diff.
7. Adversarial agents test exploits and edge cases.
8. Integration Lead runs complete validation.
9. Game Director evaluates the resulting gameplay.
10. Only then does the work merge.

## Temporary playtest agents

Future tests should include:

1. Faction agents.
2. Strategic personality agents.
3. Exploit hunters.
4. Kill web auditors.
5. Systems auditors.
6. Performance agents.
7. Interface agents.
8. Visual auditors.
9. The Armchair General.

## Model allocation

More capable models should handle:

1. Architecture.
2. Cross system design.
3. Integration.
4. Historical synthesis.
5. Difficult debugging.

Lower cost models may handle:

1. Repetitive content conversion.
2. Schema validation.
3. Test generation.
4. Interface state enumeration.
5. Long simulation monitoring.

## Human authority

The founder remains the product authority. Agent consensus does not overrule
explicit founder direction.

## Current restriction

Do not activate the coding studio during brainstorming.
